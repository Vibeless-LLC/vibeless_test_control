# Decisions

Non-trivial implementation choices, with spec section references.

## Task 1: Addressing

- **Leading-zero rows accepted (§4.1).** `A01` parses as `A1` (Excel accepts it). Canonical `ToString()` yields `A1`.
- **Solution file format (§3.1).** `Gridline.sln` is the classic format (`dotnet new sln --format sln`), since the .NET 10 default is `.slnx` and the build contract names `Gridline.sln`.
- **Shared build settings (§3.1).** `Directory.Build.props` sets LangVersion latest, Nullable, ImplicitUsings, TreatWarningsAsErrors and InvariantGlobalization for all projects.
- **`CellAddress.TryParse(ReadOnlySpan<char>)` is `internal`** and used by `RangeAddress`; the public API is the `string` overload only (no allocation when parsing ranges).

## Task 2: Value types

- **`default(CellValue)` is Blank (§9.1).** String properties are backed by `_text ?? ""` / `_error ?? ""`, so `Text` and `Error` never return null.
- **`FromText(null)` throws `ArgumentNullException` (§9.1).** The spec is silent; a null text value has no canonical form.
- **`ErrorCodes.All` is an internal `FrozenSet<string>` (§4.5).** Immutable, so it is not mutable static state; `IsValid` is the public check and is ordinal and case-sensitive.
- **`CellValue` equality is ordinal and field-wise (§9.1).** `FromNumber` normalizes -0 and rejects non-finite values, so `Number.Equals` is safe (no NaN).

## Task 3: Tokenizer

- **Tokenizer word scan and `$` placement (§5.1).** A word is `[$]?[A-Za-z][A-Za-z0-9_.]*`, followed by `$\d+` if a `$` comes next. A `$` anywhere else, a `$` with no digits after it, or a `$`-word that is not an in-bounds cell reference makes `TryTokenize` return false. A `$`-word followed directly by `(` is also a lexical error.
- **Tokenizer emits a trailing `End` token and tolerates odd numbers (§5.1).** An exponent is consumed only if digits follow it (`1e` lexes as `1`, then Name `e`), and the parser rejects the sequence. `Token.Pos` is the 0-based offset in the formula body.
- **TokenizerTests passes the expected kind as a string (§5.1).** `TokenKind` is internal and xUnit requires public test classes, so the theory parses the string with `Enum.Parse`.

## Task 4: Parser

- **Overflowing numeric literal is a parse error (§5.1, §5.4).** `1e999` parses to infinity under `double.Parse`; the parser rejects any non-finite `NumberNode` as `#PARSE!`.
- **Tokenizer failure is a parse error (§5.4).** `TryTokenize` returning false yields `ParsedFormula(null, true)`.
- **`:` is consumed only directly after a `CellRef` (§5.2).** Any other `:` (after a name, paren or number, or a third `:` in a chain) is left unconsumed and fails as a leftover or unexpected token. `A1:B2` keeps the corners as written.
- **Arity counts omitted args (§5.3, §5.4).** `PI()` has 0 args, `F(,)` has 2 omitted args. The arity lookup uses the upper-cased function name; unknown functions skip the check.
- **Deep nesting is a parse error, not a crash (§5.4).** The parser calls `EnsureSufficientExecutionStack` at expression and unary recursion and maps the resulting exception to `#PARSE!`.
- **Unary applies below `%` (§5.3).** `-2%` parses as `Percent(Unary(-,2))`, following the EBNF (`postfix = unary {"%"}`).

## Task 5: Coercion, comparison, evaluator

- **Blank flows internally; only the final result maps Blank→0 (§6.3, §6.6).** A reference to a blank cell (or a name bound to one, or a function returning Blank) yields `Blank`, so comparison's "blank adapts" rule sees it: `=A1=""` with A1 blank is TRUE. Arithmetic coerces Blank→0, `&` coerces Blank→"". `Evaluator.Evaluate` maps a top-level Blank to Number 0.
- **NumberGrammar uses ASCII digits only (§4.3 rule 5).** The regex `\d` is read as `[0-9]` (invariant culture); a hand scanner validates the shape, then `double.Parse` invariant parses the part before `%`. Non-finite results (`1e999`) are rejected; underflow (`1e-999`) is accepted as 0.
- **Left operand's coercion error beats the right operand's error (§6.4).** `"x"+#N/A` → `#VALUE!`: the left is evaluated and coerced before the right is evaluated. If the left is an error, the right is not evaluated (no observable difference; functions are deterministic).
- **`&` checks the 32,767 limit on every concatenation (§4.4)**, not only at the end, so a chain cannot build huge intermediates. The final result is also checked, covering text returned by functions.
- **Stack safety (§6.7 "recursion within a formula is acceptable").** Binary operators walk the left spine iteratively, so a left-deep chain such as 16,000 `+1` terms evaluates normally. Other recursion calls `RuntimeHelpers.EnsureSufficientExecutionStack()`; `InsufficientExecutionStackException` becomes `#VALUE!` for that formula.
- **Parenthesized references stay references (§7.0).** `Arg` unwraps `ParenNode`s before classifying, so `SUM((A1:B2))` gets a range argument (as Excel does). `(A1:B2)` in scalar position is still `#VALUE!`.
- **Arg shape (§7.0).** `IsReference` is true for a cell ref, range ref or defined name. An undefined name is classified as a direct argument (`IsReference` false, `Range` null), so `IsReference` ⇔ `Range != null` always holds and aggregation code can rely on it; `SUM(Nope)` propagates `#NAME?`. `Range` is a 1×1 `RangeRef` for a single-cell reference or a name bound to a cell, the normalized range for a range ref or range name, and null otherwise. A name's `Evaluate()` reuses the constructor's resolution, so shape and value cannot disagree. `Evaluate()` of an undefined name is `#NAME?`; of an omitted arg is Blank. Functions decide omitted-arg defaults themselves via `IsOmitted`.
- **Unknown function is decided by the Evaluator's dictionary (§5.4).** The name is upper-cased (invariant) and looked up; if absent the result is `#NAME?` and no argument is evaluated.
- **`Comparison.Compare` throws `ArgumentException` on an Error operand**; callers propagate errors first. `RangeRef.Get` throws `ArgumentOutOfRangeException` outside the range.

## Task 6: Function registry and Math functions

- **COUNTBLANK needs a reference argument (§7.1).** A direct argument (`COUNTBLANK(1)`) gives `#VALUE!`.
- **ROUNDUP when every digit lies below the rounding position (§7.1).** The brief's rule returns 0 when the cut is below 0; that is right for ROUND and ROUNDDOWN but wrong for ROUNDUP ("away from zero"). ROUNDUP of a non-zero `n` with such a cut returns `±10^(-digits)`, e.g. `ROUNDUP(0.001,-2)` = `100`, matching Excel.
- **Integer parameters saturate (§6.9).** `Coercion.TryToInt` truncates toward zero; values beyond the `int` range clamp to `int.MinValue`/`int.MaxValue`, so `ROUND(x,1E300)` returns `x` and `ROUND(x,-1E300)` returns 0.
- **Omitted arguments (§5.3, revised in fix round 1).** In variadic positions an omitted argument is absent and skipped (`SUM(,1)` = 1, `AVERAGE(1,)` = 1, `SUMPRODUCT(,)` = 0); COUNT/COUNTA do not count it. In fixed positions with no default (ABS, SIGN, INT, SQRT, MOD, POWER, ROUND*) an omitted argument is `#VALUE!` via `ArgGuard.Required`.
- **COUNT on a direct text argument** counts it only if it parses as a number under `NumberGrammar` (after trimming spaces), per the §7.1 "numeric text" rule.
- **SUMPRODUCT is sparse.** Each argument is mapped by position over its non-blank numeric cells; only positions present in every argument contribute, so cost is O(non-blank cells), not O(range area). Dimension mismatch beats an error value in a cell; otherwise the first error (argument order, then row-major) propagates. A scalar argument is a 1×1 array; booleans and text count as 0.
- **POWER reuses the `^` operator's logic** via `Evaluator.Power` (made internal), so `POWER(0,0)` is `#NUM!` and `POWER(0,-1)` is `#DIV/0!` as in §6.3.
- **Arity registry keys are upper-case**; `Register` upper-cases the name and throws on duplicates.
- **CoreTestHost (test side).** A mini interpreter of cell inputs stands in for the Workbook until Task 10 (blank, `'text`, TRUE/FALSE, number via NumberGrammar, `=formula` evaluated in listed order, else text).

## Task 7: Logic and information functions

- **IF omitted branches (§7.2, §5.3).** An omitted `t` (`IF(TRUE,,1)`) yields `0`; an omitted or absent `f` yields `FALSE`; an omitted condition is `#VALUE!`. Only the chosen branch is evaluated (`Arg` is lazy). The condition is coerced per §6.2, so `"x"` is `#VALUE!` and `"true"` is TRUE.
- **AND/OR/XOR scan (§7.2).** Reference args contribute booleans and numbers only (text and blanks are ignored; the first error propagates); direct args use §6.2 coercion; an omitted arg is absent and skipped (`AND(,TRUE)` = TRUE). NOT, IFERROR/IFNA (value, and alt when chosen) and the IS* tests give `#VALUE!` for an omitted argument (§5.3). No logical value found gives `#VALUE!`. XOR is TRUE for an odd count of TRUE values.
- **ISBLANK (§7.2)** is TRUE only for a single-cell reference (or a name bound to one) whose cell is blank; a range argument is FALSE.

## Task 8: Text functions and Wildcard

- **Wildcard (§7.3).** `IsMatch` matches the whole string; `Search` tries each start position >= start and matches a prefix of the rest (an empty match at `text.Length` counts, so `SEARCH("",t,LEN+1)` is `LEN+1`). Case-insensitive via `char.ToUpperInvariant`. A trailing lone `~` is a literal `~`. `IsMatch` uses iterative single-star backtracking. `Search` splits the pattern at unescaped stars: the first segment must match at the start position and later segments are found greedily leftmost; because tail success is monotone in the start, one tail failure returns -1, giving O(pattern*text) (the naive per-start retry was ~p*t^2 and hung on `SEARCH("a*a*a*a*b",REPT("a",32767))`). No regex, no recursion; `IsMatch` is the entry point Phase 3 reuses.
- **Omitted arguments (§5.3, revised in fix round 1).** Only documented defaults apply when a position is omitted (`LEFT`/`RIGHT` n=1, `FIND`/`SEARCH` s=1, `SUBSTITUTE` i = all). Every other omitted scalar position (text, number, boolean) is `#VALUE!` through `ArgGuard.Required`/`TryInt`, e.g. `MID("abc",2,)`, `REPT("a",)`, `FIND(,"abc")`. Variadic values (CONCAT, TEXTJOIN values) skip an omitted argument; TEXTJOIN's delimiter and `ignore_empty` are required.
- **32,767 limit (§4.4).** Every text-producing function checks the result; `REPT` and `SUBSTITUTE` check before/while building so huge intermediates are never allocated. A result of exactly 32,767 is allowed.
- **TEXTJOIN blanks.** With `ignore_empty` FALSE, blank cells in a range count as empty entries (delimiters are still emitted); they are accounted for from the sparse non-blank enumeration so a huge empty range is not scanned cell by cell. CONCAT skips blanks (they add nothing).
- **Range errors** inside CONCAT/TEXTJOIN ranges propagate (first in row-major order).

## Task 9: Dependency graph and recalc planner

- **Range index: per-column row blocks plus a per-column tall list (§6.7, §12).** Ranges are normalized and deduplicated: one `RangeEntry` per distinct range, holding its dependent set (1,000 copies of `$A$1:$A$100000` are one entry with 1,000 dependents). Each column the range spans has a `ColumnIndex`. A short range (overlapping at most 8 blocks of 256 rows) is registered in each block it overlaps. A taller range goes into the column's `Tall` list. A changed cell scans only its own block plus its column's tall list, checking `Contains`. So sliding-window ranges (`SUM(A{i}:A{i+2})`) cost O(block occupancy) per lookup instead of O(all ranges), and a full-column SUM costs one entry. An entry leaves the index when its last dependent goes.
- **Names (§6.1).** A name is a virtual node with id `-(index+1)`. It is created the first time it is referenced or defined, and it is never removed, so dependents of an undefined name stay registered and `NameDependents` can re-plan them once the name is defined. A defined target is registered in the range index with the name node as a dependent. `DirectDependents` expands a name node into its formula dependents, so cycles through names are found like any other cycle. Name keys are case-insensitive (stored upper-cased).
- **`DirectDependents` may yield duplicates** (e.g. `=A1+SUM(A1:A2)`). The planner's visited state absorbs them, and skipping a per-call dedupe set keeps the no-dependents path (P-3) allocation-light.
- **One-pass planning (§6.7).** The brief describes a DFS that collects the affected set, then Tarjan over it. Tarjan's own explicit-stack DFS, started from the roots, visits exactly that reachable set, so the planner runs Tarjan directly from the roots. Roots are the changed formula cells, the dependents of changed non-formula cells, and the dependents of changed names. The result is the same and edges are enumerated once instead of twice. The range-chain graph has O(n²) edges, so this matters. Tarjan frames hold lazy dependent enumerators on a `List<Frame>`, so memory is O(depth + nodes), and there is no call-stack recursion. A self-edge marks a cycle, as does an SCC larger than 1. SCC emission order is reversed to give `Order`. `PlanAll` runs the same pass over all formula keys, ignoring edges to keys outside that set.
- **Bulk changes (§6.7, §12; Task 9 fix round 1).** `Plan` deduplicates roots, and it expands all changed non-formula cells through `DependencyGraph.DistinctDirectDependentsOfMany`. That method expands each distinct range entry and name node at most once and yields each dependent once. A paste or clear of all 100k cells under 1,000 × `=SUM($A$1:$A$100000)` therefore costs O(changed + entries hit + affected) and allocates about 1 MB, where the earlier version made about 10^8 roots and allocated about 1.1 GB.

## Task 10: Workbook Phase 1 API

- **One mutation path (§9.2, prepares §9.3).** `SetCell` validates, then calls a private `Commit(edits)` that applies every edit (store + graph), plans once with `RecalcPlanner.Plan(editedKeys, …)`, evaluates, sets `LastRecalc` and raises `CellsChanged`. Phase 2's `ApplyBatch`/undo/redo can reuse it. `FromSnapshot` shares the per-edit `Apply` but plans with `PlanAll`. The graph is fully updated before planning and never touched during planning or evaluation.
- **Setting the same input still recalculates (§9.2).** `LastRecalc` after `SetCell(X, …)` is the formula count of {X} ∪ dependents(X), so a repeated input is re-planned and re-evaluated; since nothing changes, no event is raised. A re-set formula starts from the cell's previous value, so an unchanged result is not reported as a value change.
- **EvaluatedFormulaCount counts every formula in the plan, cycle members included (§9.2).** Cycle members are assigned `#CIRC!` rather than evaluated, but they are formula cells in {X} ∪ dependents(X); after a load the count equals the total formula count as required. Changed constants are not counted.
- **Static dependencies (§6.1).** `DependencyExtractor` walks the AST with an explicit stack and collects every `RefNode`, normalized `RangeNode` and upper-cased `NameNode`, including untaken `IF` branches (so `=IF(TRUE,1,A1)` in A1 is a cycle). A parse error or a formula without references has null deps. A formula cell that becomes a constant or blank gets `SetDependencies(key, null)`.
- **CellStore range enumeration.** Ranges of at most 64 cells probe the dictionary directly; a single-column range binary-searches its column's sorted row list; wider ranges k-way merge the column lists with a `PriorityQueue` keyed by cell key (row-major). Cost is O(occupied in range × log cols + cols × log n). `KeysRowMajor` sorts the keys on demand (only `GetUsedAddresses` uses it).
- **CellsChanged** is built only when a handler is attached: changed keys (input changed, or value changed by `CellValue.Equals`) are sorted, deduplicated and converted to canonical addresses in a fresh array.
- **FromSnapshot validation (§9.1).** All addresses, input lengths and duplicates (by cell key, so case-insensitive and `$`-insensitive) are checked before anything is built; an `""` input still counts for duplicates. Names are validated too (see the fix-wave entry on names; the original Phase 1 build rejected any name).
- **CoreTestHost (tests)** now uses the real `Workbook`: inputs are set in order, then the formula is set in Z100.

## Task 11: .gridline format and atomic save

- **Writer is hand-built (§8.1).** `GridlineFile.Serialize` appends to a `StringBuilder` using `JsonEscaper`, never `JsonSerializer`, so the bytes are exactly the spec layout (UTF-8 no BOM, LF, trailing `\n`).
- **Lone surrogates (§8.1).** `SetCell` accepts them and they cannot be UTF-8 encoded, so `JsonEscaper` writes them as `\udxxx` (lowercase hex); valid pairs are written literally. `System.Text.Json` refuses to read such a string (`GetString` throws `InvalidOperationException`), so the loader falls back to manually unescaping the raw token. The FsCheck round-trip property includes lone surrogates.
- **Missing keys (§8.2).** A missing `cells` or `names` key is treated as empty. If present, `names` must be an object with string values and `cells` an array, else `GridlineFormatException`.
- **Version (§8.2).** Accepted only if a JSON number that `TryGetInt64` accepts (so `1.5`, `1.0`, `1e0` and `"1"` are all rejected). `version > 1` gives a message containing `unsupported version`; `version < 1` gives `GridlineFormatException` ("invalid version").
- **Names (§8.1, §8.2; revised in the Phase 1 fix wave).** Entries of `names` are passed to `Workbook.FromSnapshot`, which validates them (§9.6); its `ArgumentException` for an invalid or duplicate name or `refersTo` is wrapped as `GridlineFormatException`. The writer emits `GetNames()` in the §8.1 layout, so a canonical file with names round-trips byte for byte.
- **Save (§8.4).** Temp file `path.<guid>.tmp` in the target directory (`FileMode.CreateNew`), `Flush(flushToDisk: true)`, `File.Move(tmp, path, overwrite: true)`; the temp is deleted best-effort on failure.
- **Undecodable strings and BOM (§8.2).** Any InvalidOperationException from System.Text.Json (invalid UTF-8 inside a string, lone-surrogate escapes in a name or format) is wrapped as GridlineFormatException. Property names and format go through the same tolerant unescaping as values, so a lone-surrogate name or format is handled like any other string. A leading UTF-8 BOM is skipped on load (lenient reading); the writer never emits one.

## Task 12: CLI Phase 1

- **Unknown escapes in SETX (§10.3).** `Unescape` handles `\`, `\t`, `\n`, `\r`; any other backslash sequence (and a trailing lone backslash) is left verbatim.
- **Exit codes for set (§10.1; revised in the Phase 1 fix wave).** `set` validates its arguments before touching the file, like `eval`: an invalid address gives 5 and input over 32,767 UTF-16 units gives 1 (usage), even for a missing or malformed file; then the file is loaded (missing 2, format 3). `eval` validates all addresses before loading the file.
- **Script input (§10.3).** stdin is read whole and split on `\n` only (a trailing `\r` is stripped per line), so a lone CR inside an input is preserved. Errors in SAVE/LOAD print an ERR line and the script continues; a failing LOAD keeps the current workbook.
- **ERR text (§10.3).** Messages are free-form, with tab/CR/LF replaced by spaces so each ERR is one line with exactly one tab.
- **Script command word and address** are case-insensitive; addresses are echoed in canonical form.

## Task 13: Architecture tests

- **Prefix matching (§3.2).** NetArchTest `HaveDependencyOn("System.IO.File")` is a prefix match, so it would also flag `System.IO.FileInfo`/`FileSystemInfo`/`FileAccess`. Core uses none of those, so the strict prefix is accepted.
- **Namespace filters (§3.3).** Per-namespace rules use the exact sub-namespace (`Gridline.Core.Parsing`, ...); `Gridline.Core.Addressing` forbids each sibling sub-namespace explicitly. Dependencies on root `Gridline.Core` types are not forbidden by §3.3 and are not checked. The Commands rules passed vacuously in Phase 1; Phase 2 added `Gridline.Core.Commands` and the App rule (`App_does_not_depend_on_Cli`).
- **Mutable static check (§3.2).** Reflects over Core, IO and Cli publicly visible types; flags public static fields that are neither const nor readonly and public static properties with a public setter, ignoring compiler-generated names containing `<`.

## Task 14: Performance budgets (§12 P-1–P-5, P-7)

- **Harness (§12).** `tests/Shared/PerfHarness.cs` is linked (`<Compile Include … Link>`) into Gridline.Core.Tests and Gridline.IO.Tests rather than duplicated. `Median(setup, measured, runs = 5)` does one warm-up, then 5 timed runs; `setup` and a full GC run before each run, outside the timing. P-3 times each of its 1,000 `SetCell` calls separately and takes the median. P-7 memory is `PrivateMemorySize64` after `GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect()`, with the last loaded workbook still alive; the test host is included.
- **Serial perf runs.** Perf tests are in the `Perf` collection (`DisableParallelization = true`, so it runs alone after the parallel collections). Its collection fixture `PerfLock` holds an exclusive lock file in the temp directory, because `dotnet test Gridline.sln` runs the two test assemblies in parallel processes; the lock keeps Core and IO perf tests from overlapping. The two timed dependency-graph tests live in `DependencyGraphPerfTests`, also in the `Perf` collection (moved there in the Phase 1 fix wave).
- **Workloads.** P-1/P-3/P-5 use the brief's workbook: A1:A50000 = 1..50000, B{i} = `=A{i}+A{i+1}*2`, B50000 wraps to A1. P-1's JSON is built by hand in the test (not by the writer under test). P-2 and P-4 reuse one workbook: `setup` restores the original input (outside the timing), then the timed edit is applied. P-7 "load" is `GridlineFile.Load` of the hand-built file bytes (revised in the Phase 1 fix wave; it was `Workbook.FromSnapshot`), median of 5 loads; the test lives in Gridline.IO.Tests with P-1 and P-5. Measured ~1.5 s, 74 MB private memory.
- **Measured, then optimized only P-7 (Release, dev machine).** Before → after:
  P-1 load 162–245 ms → ~230 ms (budget 1.5 s; unchanged code path, run-to-run noise);
  P-2 chain edit 26 ms → 27–33 ms (250 ms);
  P-3 no-dependents edit median < 0.1 ms → 0.001 ms (1 ms);
  P-4 SUM edit 7.3 ms → 2.6 ms (50 ms);
  P-5 save 22.6 ms → 22.5 ms (1 s);
  P-7 load 2,423 ms → ~1,590 ms, private memory 46–60 MB (5 s, 600 MB).
  Only P-7 was within ~2x of its budget, so only it was optimized; every budget now has at least 3x headroom.
- **P-7 fixes.** (1) Aggregates (SUM, AVERAGE, MIN, MAX, PRODUCT, SUMSQ) fold numbers as they are enumerated through a struct `IAccumulator` instead of collecting them into a `List<double>` and calling LINQ. A 100k-cell SUM used to grow a list to 1 MB on the large object heap, and 1,000 of them allocated about 1 GB. The fold order (argument, then row-major) is the same as before; `Enumerable.Sum` over doubles is a sequential loop, so results are bit-identical. MIN/MAX keep the first extreme, like LINQ. (2) `CellStore` keeps each column's cells in a list parallel to its sorted row list, and `EvalContext.EnumerateNonBlank` reads a single-column range straight from those lists, with no dictionary lookup per cell. Multi-column ranges still use the key merge.

## Phase 1 final-review fix wave

- **BOM on script stdin (§10.3).** `gridline script` strips one leading U+FEFF from the stdin text before splitting lines, so a client writing with .NET's `Encoding.UTF8` (which emits a preamble) does not get `unknown command` on line 1. Only one BOM, only at the very start; a BOM anywhere else is ordinary input.
- **Whitespace-only script lines are blank (§10.3).** A line for which `string.IsNullOrWhiteSpace` holds (after the CR strip) is ignored like an empty line.
- **Unusable paths are I/O errors (§10.1).** An `ArgumentException`/`NotSupportedException` from path handling (empty path, embedded NUL, unsupported form) in `eval`, `set` (source or `--out`) or `script --file` maps to exit 2 with a single-line `error: invalid path: …` message (the path itself is not echoed, since it may contain NUL). Only the file read and `Path.GetFullPath` calls are wrapped, so an `ArgumentException` from anywhere else is still a bug, not exit 2. `GridlineFile.SaveToPath` resolves the target with `Path.GetFullPath` before creating the temp file, so an invalid target throws before anything is written and the temp file is always beside the target (never in the working directory).
- **Huge version numbers (§8.2).** `version` must be spelled as an integer (digits, optional leading `-`; no fraction or exponent), checked on the raw token before `TryGetInt64`. An integer too large for Int64 is reported as `unsupported version` (positive) or `invalid version` (negative), so `99999999999999999999` is a future version, not "not an integer". `1.0`, `1e0` and `1E20` are still "not an integer".
- **Names: Phase 1 storage and evaluation subset (§8.1, §8.2, §9.6; controller ruling).** Rejecting every file with a non-empty `names` object broke the §8.1 round trip, so Phase 1 now loads, stores, saves and evaluates names; public `DefineName`/`DeleteName` arrived in Phase 3. `Gridline.Core.Addressing.NameRules` holds the rules both phases use: `IsValidName` (`^[A-Za-z_][A-Za-z0-9_.]{0,254}$`, not `TRUE`/`FALSE` case-insensitively, not `^[A-Za-z]{1,3}[0-9]+$`), `TryParseRefersTo` (fully absolute `$COL$ROW` or `$COL$ROW:$COL$ROW`, in bounds, letters any case, corners any order) and `FormatRefersTo` (canonical uppercase, normalized corners). `FromSnapshot` validates every name before building anything; names are unique under `OrdinalIgnoreCase`.
- **Canonical `refersTo` (§9.6).** Stored and saved canonical: `$a$1` → `$A$1`, `$C$10:$A$1` → `$A$1:$C$10`, `$A$01` → `$A$1`. A range whose corners coincide (`$A$1:$A$1`) is stored as the single cell `$A$1` and behaves like a cell name. A non-canonical file therefore loads fine but does not save byte-identically (only canonical files must).
- **`#REF!` names (§9.6).** `refersTo` exactly `#REF!` (case-sensitive, like error literals) is accepted so Phase 3 files round-trip. Such a name has no target (`SetNameTarget(name, null)`), is not a reference argument, and evaluates to `#REF!` (`SUM(Gone)` propagates it). The evaluator asks `IEvalContext.UnresolvedNameValue` for the value of any name `TryResolveName` does not resolve: `#NAME?` when undefined, `#REF!` for a `#REF!` name (default interface method returns `#NAME?`, so test contexts need no change).
- **Name evaluation and dependencies (§6.1, §6.7, §9.6).** `TryResolveName` looks names up case-insensitively; `isRange` is true when the target has more than one cell. Cell name ≈ cell reference, range name ≈ range (`=Total` alone → `#VALUE!`, `=SUM(Total)` aggregates), undefined → `#NAME?`. Each name's target is registered with `DependencyGraph.SetNameTarget` (upper-cased key) before the load recalc, so editing a cell inside a target recalculates the name's dependents, and a formula reaching its own cell through a name is a cycle (`#CIRC!`). Names do not count in `EvaluatedFormulaCount`.
- **Underscore names are lexically unreachable (§5.1 vs §9.6).** `_x` is a valid name, but §5.1 word tokens start with a letter, so a formula mentioning `_x` is `#PARSE!`. The name still loads, saves and appears in `GetNames()`. Not changed: the tokenizer follows §5.1 exactly.
- **Arity table is pinned by a test (§7.0–7.3, §5.4).** `ArityTests` writes the 50 Phase 1 arities out from the spec tables and checks them against the registry and end to end (min and max parse; min−1 and max+1 are `#PARSE!`; 256 args to a variadic is `#PARSE!`). Reading of the tables: a variadic `f(v1,…)` needs at least one argument (max 255); `TEXTJOIN(d,ignore_empty,…)` needs at least 3; `ROUND`/`ROUNDUP`/`ROUNDDOWN` require `d` (2–2); `IF` takes 2–3, `LEFT`/`RIGHT` 1–2, `FIND`/`SEARCH` 2–3, `SUBSTITUTE` 3–4.

## Phase 2

- **Printer and shifter stack safety (§5.5, §9.4).** `FormulaPrinter` and `ReferenceRewriter` walk the left spine of `BinaryNode` chains iteratively (as the Evaluator does), so a 16k-term `1+1+...` formula prints and shifts without recursion; other node kinds recurse, bounded by the parser's nesting limit. `ReferenceRewriter.Shift` returns the original `RefNode`/`RangeNode` instances when nothing moves, and `changed` is true only if some reference moved or became `#REF!`. Name nodes print `nameCasing(NAME.ToUpperInvariant()) ?? as written`.
- **Undo history (§9.3).** `Gridline.Core.Commands` holds `CellEdit`, `EditStep` and `UndoHistory`; only `Workbook` uses it (Evaluation/Functions/Dependencies/Parsing stay independent, §3.3). A step stores input diffs only (old/new input strings per distinct key, never values) plus, when names changed, the complete sorted name lists before and after (null = names unchanged). Undo/redo re-enter the single `Commit` path with `record: false`, building each edit's `OldInput` from the store, so they recalc once over the union of changed keys (+ dependents) and changed names and raise `CellsChanged` once. Step Ids come from a per-workbook counter and are never reused, so a position Id is unambiguous.
- **Dirty tracking (§9.3).** Position = Id of the top undo step, or `BaseId` (0, then the Id of the most recently dropped step). `IsDirty = CurrentPosition != SavedPosition || savedPositionLost`; "lost" is set when a push discards the saved step from the redo stack, or when a drop leaves `SavedPosition` neither `BaseId` nor on either stack; `MarkSaved` clears it. Saving at the step that is later the oldest dropped one therefore stays reachable (undo-all lands on it and is clean). New and loaded workbooks start clean with empty history.
- **No-op mutations (§9.3, §9.2).** `Commit` drops edits whose new input equals the pre-commit input (ordinal). `ApplyBatch` validates all addresses and inputs first, dedupes by key (case-insensitive address, last wins, first-occurrence order) and compares against pre-commit inputs, so A→B→A in one batch is a no-op (fixes the Phase 1 caveat). A no-op batch (or empty batch) creates no step, raises no event and sets `LastRecalc` to 0. A no-op `SetCell` creates no step, raises no event and is not dirty, but keeps the Phase 1 behaviour of re-evaluating {X} ∪ dependents(X) (pinned by `SettingSameFormula_ReevaluatesButRaisesNoEvent`, §9.2's literal rule).
- **Names in steps (§9.3).** Internal `Workbook.ReplaceNames(list)` validates every name/`refersTo` and case-insensitive uniqueness, canonicalizes, and commits the whole list as one step (none if identical, casing included; a casing-only change is a step). The public `DefineName`/`DeleteName` (Phase 3, see "Phase 3: defined names") build the new list and call it. A removed name keeps its graph node with a null target, so its formulas reconnect when it is redefined (or the deletion undone). Names whose target changed, appeared or disappeared are passed to the planner. `CellsChanged` still carries cell addresses only.
- **Event after history (§9.2, §9.3).** `Commit` pushes the undo step before raising `CellsChanged`, so handlers see final `IsDirty`/`CanUndo`/`CanRedo` (Undo/Redo move the history before committing, so the same holds there). A throwing subscriber propagates to the caller, but the mutation is complete and its step recorded, so it can still be undone; the event is the last thing a mutation does.
- **Formula nesting depth is bounded (§5.4, §6.7).** `Parser.MaxDepth = 256` (lowered from 1024 in review so every shape parses, evaluates, prints and shifts identically on a 1 MB thread with wide margin; Excel caps function nesting at 64): formulas whose AST nests deeper than 256 levels are `#PARSE!`. Depth is the walker recursion depth, with `BinaryNode` left spines excluded (walkers iterate them, so a 16k-term `1+1+...` still parses): each unary sign, each `%`, each parenthesis pair, each call (over its deepest argument) and each binary right operand adds one level, and the leftmost operand of a binary chain adds one level (walkers recurse into it even though the spine is iterated). Every parser-produced AST is therefore safe for the recursive walkers (printer, shifter, dependency extractor, evaluator) on a small stack; `EnsureSufficientExecutionStack` stays as a backstop. To keep per-level stack cost small the parser is a single precedence-climbing `Expr` method (same grammar and left associativity as before), and `FormulaPrinter.Write` / `ReferenceRewriter.Walk` keep their bulky cases in separate non-recursive helpers (printing and shifting a MaxDepth-deep tree is tested on a 256 KB thread). In practice the usable nesting is lower than 256 for some shapes: a binary operation inside parentheses costs several levels per nesting step, so such shapes (e.g. `((((1+1)+1)+1)...`) reach `#PARSE!` at roughly 128 nested levels.
- **CopyPaste (§9.4).** `Workbook.CopyPaste(sourceRange, destinationTopLeft)` validates the source (cell or range, corners in any order), the destination address and the destination extent before touching anything (`ArgumentException`: no step, no event, not dirty). It snapshots the source inputs, builds one `CellEdit` per destination cell and routes them through `Commit` (one step, one recalc, one event). Blank source cells give `""`; non-formula inputs are copied verbatim; a formula that is a parse error is copied verbatim (it has no AST to shift and rewriting it would lose the text); every other formula is `FormulaPrinter.Print(ReferenceRewriter.Shift(root, dRow, dCol))`, so it is canonical even at offset zero, and name references use the defined casing. The undo property test gained a `Paste` op whose destination stays inside the observed pool.
- **CLI Phase 2 script commands (§10.3).** `UNDO`/`REDO` print `OK`/`NOOP`, `DIRTY` prints `TRUE`/`FALSE`, `PASTE <src> <dst>` prints nothing (exactly two space-separated arguments, otherwise ERR), and `SAVE` calls `MarkSaved()` after the save succeeds. `BEGIN` opens a batch in which `SET`/`SETX` lines are buffered as written (validation happens at `END`, see "CLI BEGIN…END validates at END" under Phase 2 final-review fixes); `END` closes it and applies the buffer with one `ApplyBatch` (the batch is closed even if the apply throws, which prints one ERR and applies nothing). Any other command inside a batch, including `UNDO`/`REDO`/`DIRTY`/`PASTE`/`SAVE`/`LOAD`/`GET`, prints ERR and is not executed; the batch stays open. `END` without `BEGIN` and `BEGIN` inside an open batch are ERR (the latter keeps the existing batch open). At end of input an unclosed batch is discarded and `ERR\tunterminated BEGIN` is printed (exit 4).
- **Pasted input length (§9.4, §4.3; controller ruling).** Re-emitted formulas can be longer than the source (references shift to longer addresses, or become `#REF!`). `CopyPaste` checks every pasted string against `MaxInputLength` (32,767) before committing; if any exceeds it, it throws `ArgumentException` and changes nothing (no step, no event, not dirty).
- **App shell (§11.1, §11.2, §11.5, §11.7, §3.2).** `Gridline.App` (net10.0-windows, WinExe, Core + IO only) keeps all document logic in the UI-free `DocumentSession` (workbook, path, `Title`, `StateChanged`, `SessionId`); `MainWindow` code-behind only wires commands and copies `Title`. `StateChanged` follows the current workbook's `CellsChanged` (resubscribed on New/Open) plus explicit raises after save/new/open. `InvariantGlobalization=true` from Directory.Build.props works for WPF (app launches), so no override. WPF projects drop the `System.IO` implicit using, so App files add it explicitly. The placeholder grid host is a `Label` (a bare `Border` has no UI Automation peer, so `AutomationId=Grid` would not be findable); Replaced by `GridControl` (see "Virtualized grid"). Copy/Paste menu items use `ApplicationCommands`; the window bindings were added with the clipboard work (see "Clipboard"). Unsaved-changes prompts are covered under "File commands and unsaved-changes prompt". `Gridline.Architecture.Tests` now targets net10.0-windows because a net10.0 project cannot reference the App; its helper asserts the selected type set is non-empty (except `Gridline.Core.Commands`) so a rule can never pass vacuously, and the static-state rule also scans App.
- **Virtualized grid (§11.3, §11.7).** `GridControl` is a `FrameworkElement` that draws in `OnRender` only the visible headers and cells (the partially visible trailing row/column included), building one `FormattedText` per visible non-blank cell per frame (text truncated to 256 chars, one line, ellipsis) and grid lines as one frozen `StreamGeometry`; nothing enumerates rows or the workbook, so cost per frame is O(visible cells) at any scroll position. Fixed 22 px rows, 80 px columns, 56 px row header. The host `Grid` in `MainWindow` holds the control plus a vertical `ScrollBar` (1..100000 → `TopRow`) and horizontal one (1..702 → `LeftCol`), so the last row/column can be scrolled to the top/left edge (the rest of the viewport is empty); `ViewportChanged` keeps the bars' value/viewport in sync. The wheel scrolls 3 rows per notch. Header clicks select whole rows/columns and open the header context menu (Phase 3, see "Phase 3 Task 8"); Shift+click and drag extend, and dragging past the edge auto-scrolls. A custom `FrameworkElement` has no UI Automation peer by default, so `OnCreateAutomationPeer` returns a `FrameworkElementAutomationPeer` subclass with control type `DataGrid` and class name `GridControl`; it is keyboard-focusable, and `AutomationProperties.AutomationId="Grid"` is set in XAML. `GridSelection` (anchor + active, normalized `Range`, clamped `MoveTo`/`MoveBy`, `Changed` only on an actual change) and `CellFormatter` are UI-free and unit-tested.
- **Editing, name box, formula bar, status bar (§11.4, §11.7).** Logic lives in UI-free, unit-tested classes: `GridKeyMap` (key + modifiers → grid action / editor action, printable-text test) and `SheetController` (begin/commit/cancel edit, formula-bar commit, name-box navigation, Delete, status texts). `MainWindow` only moves text between controls and the controller. The in-cell editor is a `TextBox` (AutomationId `CellEditor`, MaxLength 32,767) on a `Canvas` overlaid on the grid (offset by the header sizes, clipped, null background so clicks reach the grid). A printable `TextInput` on the grid starts an edit with that text, F2 with the existing input; Enter/Tab commit and move down/right (Shift reverses), Esc cancels. The commit writes to the address where the edit began with one `SetCell` (one undo step). Losing keyboard focus to another element commits without refocusing the grid, so the clicked element (formula bar, name box, a cell) keeps focus; only Enter/Tab/Esc and commands return focus to the grid. If the commit throws, the edit stays open and an error is shown. The editor overlay's offset and size come from the `GridControl` layout constants; losing it because the window was deactivated (`NewFocus == null`) keeps the edit open. Also Enter/Tab on the grid without an edit move like Excel; Home / Ctrl+Home / PageUp / PageDown are supported; Ctrl+arrows are not.
- **Delete and the selection sum (§11.4, §11.7).** Both work on the used cells inside the selection: a range of at most 4,096 positions is scanned cell by cell; a larger one filters a fresh `GetUsedAddresses()` on every read (no cache: a cache invalidated from `CellsChanged` returned stale sums to handlers subscribed earlier, e.g. `DocumentSession.StateChanged`; worst case about 30 ms per read for a full-sheet selection over 100k used cells), so a full-sheet selection never builds a 70M-entry batch or loop. Delete issues one `ApplyBatch` of `""` edits for those cells (nothing, and no step, if there are none). `SelectionSum` is the sum of Number values, `G10` invariant (`0` when there are none); `SelectionValue` is `GetValue(active).ToCanonicalString()`.
- **Name box and formula bar (§11.4).** Name box Enter: `CellAddress.TryParse(text.Trim())` (single cell, `$` allowed, any case); success selects and scrolls the cell into view, failure reverts; Esc reverts; focus returns to the grid in every case, and losing focus reverts. Formula bar Enter commits with one `SetCell` on the active cell and returns focus to the grid; Esc reverts; losing focus without Enter discards the typed text (it is not committed). While an in-cell edit is open the formula bar mirrors the editor's text. Neither box is overwritten while it has keyboard focus.
- **Undo/Redo routing (§11.5, §11.7; controller question).** When the grid has focus, Ctrl+Z/Ctrl+Y reach the window's `ApplicationCommands.Undo/Redo` bindings → `Workbook.Undo/Redo`. When a TextBox (name box, formula bar, in-cell editor) has focus, the TextBox's own class bindings handle Ctrl+Z/Ctrl+Y as **text** undo, as in Excel's edit mode; the workbook is not touched. The Undo/Redo menu items do not use routed commands (their `CanExecute` would follow whichever element has focus, e.g. a TextBox's text-undo stack): they call the workbook directly and their `IsEnabled` is set from `CanUndo`/`CanRedo` on every session state change. Opening a menu takes focus from the in-cell editor, which therefore commits first, so "Undo" from the menu during an edit undoes that just-committed edit; after any submenu closes, focus returns to the grid unless a visible TextBox has it (WPF would otherwise try to restore focus to the collapsed editor and leave nothing focused).
- **InvariantGlobalization off for the App (§11).** With `InvariantGlobalization=true` (Directory.Build.props) the app launched, but the first time any TextBox received keyboard focus WPF crashed with `CultureNotFoundException` (`InputLanguageSource.CurrentInputLanguage` → `new CultureInfo(1033)`). `Gridline.App.csproj` sets it to `false`; Core/IO/Cli keep invariant mode, and App code still formats with `CultureInfo.InvariantCulture` explicitly. This supersedes the "works for WPF" note in the App shell entry above.
- **File commands and unsaved-changes prompt (§11.5).** Flow logic is UI-free in `DocumentLifecycle` (New/Open/Save/SaveAs/Exit/`ConfirmDiscard`) with injected `IUnsavedChangesPrompt` (Save/DontSave/Cancel), save/open path pickers (null = cancelled) and an error reporter; unit-tested without dialogs. Save on an untitled document runs Save As; a cancelled or failed Save aborts the original action (failure is reported). Open prompts first, then picks a file; a load failure is reported and the document kept. Window close button and File > Exit share one `Closing` handler (an in-cell edit is committed first; if the commit fails the close is cancelled). The dialog (`UnsavedChangesDialog`, title "Gridline", AutomationIds `SaveButton`/`DontSaveButton`/`CancelButton`) is a fresh modal window per prompt. File dialog filter is `Gridline (*.gridline)|*.gridline`. `DocumentSession` gained `DocumentName` and `IsDirty` (currently the workbook's).
- **Autosave and recovery (§11.6, §11.7).** `RecoveryService(dir, sessionId)` writes `<dir>\<session-guid>.gridline` via `GridlineFile.SaveToPath` (creating the directory) only when dirty; `FindRecoveryFiles` lists the other `*.gridline` files, oldest first; `Delete` ignores a missing or locked file. `RecoveryService.ResolveDir()` returns the `GRIDLINE_RECOVERY_DIR` environment variable when set (UI tests use a temp folder), else `DefaultDir` (`%LOCALAPPDATA%\Gridline\Recovery`). A `DispatcherTimer` in `MainWindow` (interval injectable via the constructor, 60 s by default) calls `AutosaveIfDirty(session)`; IO errors are ignored until the next tick. The recovery file is deleted on a successful Save/Save As (`DocumentSession.Saved`), when the session becomes clean again (undo to the saved state, New, Open), and when the window actually closes (`Closed` does not fire if the user cancels the exit prompt).
- **Restored documents (§11.6).** `DocumentSession.TryOpenRecovered` loads with `GridlineFile.LoadFromPath` and sets a `_recovered` flag (the brief's `RecoveredFrom`): the document is untitled and `IsDirty` (and so the title ` *`, the exit prompt and autosave) is `Workbook.IsDirty || _recovered`; a Save As, New or Open clears it, and the workbook's own history is untouched. A corrupt file leaves the session unchanged; `RecoveryDialog` reports the error and offers to discard that file. `RecoveryDialog` (AutomationId `RecoveryDialog`; per-row `RestoreButton`/`DiscardButton`) is shown modally right after the main window is shown (ApplicationIdle). Restore asks to discard a dirty current document first; because one window holds one document, after one successful restore the remaining Restore buttons are disabled and those files stay on disk for the next start (Discard still works).
- **Recovery locks and failure handling (§11.6).** Each `RecoveryService` creates `<session-guid>.lock` in the recovery dir (on first autosave or lookup) and holds it open with `FileShare.None` and `DeleteOnClose` until `Dispose` (called when the window closes), so a crash also releases and removes it. `FindRecoveryFiles` skips any `<guid>.gridline` whose lock cannot be opened exclusively (a live instance owns it), and removes openable stale locks. It never throws (an unusable directory gives an empty list). The autosave tick catches every exception and shows "Autosave failed" once in the status bar (`AutosaveStatus`), clearing it on the next success; recovery lookup at startup is guarded the same way. After a successful Restore the session autosaves immediately. New/Open/Save/Save As abort if committing the in-cell edit fails, like the close handler.
- **Clipboard (§11.6, §8.5, §9.4; controller rulings).** `DelimitedReader.Parse(text, delimiter)` (Gridline.IO, shared with Phase 3 CSV import) is a single-pass RFC 4180 reader: CRLF/LF/CR in any mix, a final terminator adds no row, a blank line is one record with one empty field, a trailing delimiter yields a final empty field, a bare `"` in an unquoted field is literal, text after a closing quote up to the next delimiter is kept literally, an unterminated quote, more than 100,000 records or more than 702 fields in a record throw `GridlineFormatException`. `DelimitedMapping.ToInput` is the §8.5 mapping. `ClipboardService` (UI-free; `IClipboard` abstraction, WPF only in `WpfClipboard`) copies the displayed values (`CellFormatter` text) as TSV with CRLF between rows, **clipped to the intersection of the selection with the used cells' bounding extent**: the selection's top-left is kept, rows/columns beyond the last used row/column inside the selection are omitted, and an empty intersection puts `""`. A clipped area over 4,000,000 positions cannot be rendered sensibly, so the system clipboard gets `""` and the status bar says the copy works within Gridline only. Paste compares the clipboard text with the text this app last set (and requires the same workbook instance, so New/Open drop the internal source); if equal it calls `Workbook.CopyPaste(source, active)`, otherwise it parses external text with Tab and writes the mapped fields (blank fields write `""`) at the active cell in one `ApplyBatch`, dropping fields beyond row 100,000 / column 702. A `GridlineFormatException`, an over-long input, or an off-grid internal destination shows a status message and changes nothing. A clipboard with no text pastes nothing; an empty clipboard text is treated as our own only when the last copy was itself empty/oversized. Clipboard access (`ExternalException`, which covers `COMException`) is retried 5 times, 40 ms apart, then reported ("The clipboard is busy"); it never throws out of the service. Ctrl+C/Ctrl+V and the Edit menu go through window command bindings (disabled during an in-cell edit); a focused TextBox keeps its own text clipboard behaviour. Status text is shown in the `ClipboardStatus` status-bar item.
- **CopyPaste is sparse (§9.4; controller ruling).** `Workbook.CopyPaste` no longer allocates rows*cols arrays: it collects only the populated source cells (read from the per-column sorted lists, so cost is O(columns + populated cells)), emits their re-emitted inputs at the shifted keys, and adds `""` edits for populated destination cells the source leaves blank. Edits are sorted by key (row-major), so semantics, the length check and the single undo step are unchanged; a whole-grid source completes in milliseconds with a bounded allocation (tested < 64 MB).

## Phase 2 final-review fixes
- **CLI BEGIN…END validates at END (§10.3, §9.3).** Inside a batch, `SET`/`SETX` buffer the address text exactly as given (a bare `SET` buffers an empty address) and `SETX` is unescaped on arrival (unescaping cannot fail). END hands the buffer to one `ApplyBatch`, which validates every address and input length before changing anything, so any bad line yields exactly one `ERR` line at END, nothing is applied, and the batch is closed. Valid batches remain one undo step.
- **GUI never dies on unexpected exceptions (§11, §9.3).** The formula bar commits through `SheetController.TryCommitInput`, which catches `ArgumentException` (e.g. input over 32,767 UTF-16 units from a UIA `ValuePattern.SetValue`), shows the message and leaves the text and focus in place; nothing is applied. `App` installs a last-chance `DispatcherUnhandledException` handler (message box, `Handled = true`) and logs `AppDomain.UnhandledException` / `TaskScheduler.UnobservedTaskException` (best effort) to `%LOCALAPPDATA%\Gridline\error.log`.
- **Paste timing assertion is a Perf test (§9.4, §12).** The `< 2000 ms` whole-grid paste check lives in `CopyPastePerfTests` (Category=Perf, serial Perf collection); the < 64 MB allocation bound stays in the default category.

## Phase 3: defined names
- **DefineName/DeleteName (§9.6, §9.3).** Public `DefineName(name, refersTo)` / `DeleteName(name)` route through `ReplaceNames`, so each is one undo step with a names-only `EditStep`. Invalid name or `refersTo` (including `#REF!` and relative/mixed refs) throws `ArgumentException` with no change; `#REF!` is accepted only by `FromSnapshot` so files round-trip. Redefining replaces the definition with the new casing (a casing-only change is a step); identical casing and target is a no-op (no step, no event). `DeleteName` of an unknown name throws; dependents recalculate to `#NAME?`.
- **refersTo keeps its form (§9.6).** A cell stays a cell (`$B$1`); a range stays a range even when 1x1 (`$A$1:$A$1`), in `GetNames()`, the file and the CLI. A 1x1 range name behaves as a range (`=R` alone is `#VALUE!`, `SUM(R)` works). `NameRules.FormatRefersTo(range, asRange)` carries this; the earlier collapse of `$A$1:$A$1` to `$A$1` was removed.
- **CLI NAME/UNNAME/NAMES (§10.3).** `NAME <name> <refersTo>` and `UNNAME <name>` take exactly two / one space-separated arguments (otherwise ERR, any workbook exception is one ERR); `NAMES` prints `NAME<TAB>name<TAB>refersTo` lines. Inside `BEGIN` they are ERR.

## Phase 3: insert/delete rows and columns
- **Structural edits (§9.5, §9.1).** `InsertRows/DeleteRows/InsertColumns/DeleteColumns` validate arguments first (`ArgumentOutOfRangeException`: insert needs `1 ≤ at ≤ max`, `count ≥ 1`; delete needs `1 ≤ at`, `count ≥ 1` and `at + count - 1 ≤ max`, computed in 64-bit; columns use `MaxColumns`). `count ≥ 1` is also required for delete (the spec's span rule alone would accept 0). An insert that would push any cell with input past the last row/column throws `InvalidOperationException` (checked per column in O(columns)). The new full cell map is then computed: a moved cell keeps its exact input unless it is a non-parse-error formula with at least one changed reference, which is re-emitted by `FormulaPrinter` with the current name casing (§5.5); parse-error formulas move verbatim. **If a re-emitted formula would exceed `MaxInputLength`, the call throws `InvalidOperationException` and changes nothing** (controller ruling; same exception type as the structural overflow). The old and new maps are diffed into `CellEdit`s (sorted row-major) and names are adjusted; everything goes through one `Commit`, so it is one undo step, one recalc and one `CellsChanged`; a call that changes no input and no name records no step.
- **Reference adjustment (§9.5, §5.5).** `StructuralShift.TryShiftIndex/TryShiftSpan` implement the table in 64-bit arithmetic (any `count` is safe). On insert, a span whose low end would pass the max fails (`#REF!`); if only the high end passes the max it is **clamped to the max** (`B99990:B100000` + 5 rows at 2 → `B99995:B100000`). `ReferenceRewriter.Structural` shifts only the edit's axis; a changed single ref keeps its `$` flags; a range is normalized first and, only if its span changes, re-emitted top-left:bottom-right with each component's `$` flag taken from the written corner that supplied it (ties: the first corner), e.g. `$B3:A$1` after inserting row 2 → `A$1:$B4`; an unchanged reversed range is left as written. `Shift` (paste) and `Structural` share one stack-safe walker with a pluggable leaf mapping.
- **Names under insert/delete (§9.6).** Each target is shifted with `TryShiftSpan` on the edit's axis; the form is kept (a cell stays a cell, a range — including 1x1 — stays a range); a fully deleted target becomes `#REF!` (null target, evaluates to `#REF!`). Undo restores the exact prior names via the step's name lists.
- **Bulk store writes (§12).** `Commit` interprets every edit first (graph updated per key; keys are distinct so each reads the pre-commit cell) and then writes them with `CellStore.SetMany`, which rebuilds any column receiving more than 16 writes by one linear merge of its sorted lists instead of one `List.Insert/RemoveAt` per write. Deleting the top half of a 100k-row column (and undoing it) therefore takes ~80 ms (undo ~50 ms) instead of O(n²) list shifting. Perf tests (Category=Perf): 100k cells (P-1 workload) insert/delete/undo at row 1 < 2 s each (measured ~140/165/55 ms); single-column 100k delete of 50k rows and undo < 2 s.
- **Key packing constant.** `CellAddress.KeyStride` (1024) and `CellAddress.KeyOf(row, col)` replace the literal in `CellStore` and `Workbook` (the files touched here); `DependencyGraph.MaxCol` is unchanged.
- **Name form change recalculates (§9.6; bug fix found by the extended undo property).** Redefining a name from a 1x1 range to the same cell (or back) changes evaluation (`=R` is `#VALUE!` for a range), so `InstallNames` now treats a change of form as a changed name and recalculates its dependents.
- **CLI (§10.3).** `INSERTROWS <row> <n>`, `DELETEROWS <row> <n>`, `INSERTCOLS <col> <n>`, `DELETECOLS <col> <n>` (column letters, any case, via `ColumnName.TryParse`) print nothing. Exactly two single-space-separated arguments; numbers are ASCII digits only, 1..int.MaxValue; anything else, or any exception from the workbook (out of range, overflow), prints one `ERR` line. Inside `BEGIN` they are ERR like other non-SET commands. The `not implemented` stub and its test are removed (every script command is now implemented).
- **Undo property (§9.3).** The FsCheck generator gained `InsRows/DelRows/InsCols/DelCols` ops (at 1..4, count 1..2). Because cells can leave the A1:C3 pool, the model now also observes every used cell (inputs and values), and the full-recalc comparison loads all used cells.

## Phase 3: lookup and reference functions (§7.4)
- **Lookups (§7.4, §6.9).** VLOOKUP/HLOOKUP/MATCH/INDEX require a reference table/range; a non-reference gives `#VALUE!` (or the argument's own error, e.g. an undefined name). An error lookup value propagates first. Exact match is same-kind only (numbers exact, booleans by value, text via `Wildcard.IsMatch`, case-insensitive); a Blank lookup value or Blank/Error key never matches exactly. Approximate search is a binary search over `RangeRef.Get` for the last key ≤ v (MATCH -1: last key ≥ v), comparing same-kind keys only (see "Phase 3 fix round 1"); results on unsorted or error-bearing data are unspecified. Argument order of checks: lookup value, table, index/type coercion errors, then `index < 1` → `#VALUE!`, `index > width` → `#REF!`.
- **INDEX bounds (§7.4).** An omitted `r` is `#VALUE!` (§5.3). A zero `r` or `c` is `#VALUE!` (checked before bounds); a negative index is also `#VALUE!` (see "Phase 3 fix round 1"); a positive index past the range is `#REF!`. With `c` omitted a single-row range indexes its columns, a single-column range its rows, and a 2-D range is `#VALUE!`.
- **MATCH (§7.4).** The type is truncated (§6.9): >0 ascending, 0 exact, <0 descending. A 2-D range is `#N/A`.
- **ROW/COLUMN/ROWS/COLUMNS (§7.4).** A non-reference argument to ROW/COLUMN is `#VALUE!` (its own error if it is one). ROWS/COLUMNS of a scalar give 1 (brief ruling); an error scalar propagates. An omitted ROW/COLUMN argument uses the formula's own cell (so ROW moves with insert/delete).

## Phase 3: criteria and conditional aggregation (§7.5)
- **Criteria parsing (§7.5, §4.3).** Text is split into the longest operator (`<=`, `>=`, `<>`, then `=`, `<`, `>`) and an untrimmed operand: a number if it matches the §4.3 rule 5 grammar, a boolean if `TRUE`/`FALSE` (any case), else text. A number or boolean criteria value means equality; a Blank criteria value (e.g. a reference to an empty cell) is treated as the number 0, per Microsoft's COUNTIF docs, so it matches numeric 0 only and not blank cells; this is distinct from the text criterion `""`, which still matches Blank cells and `""` text; an Error criteria value is returned by the function.
- **Matching (§7.5, §6.10 item 8).** A number operand matches Number cells only with the operator applied (including `<>`: only numeric cells that differ); a boolean operand matches Boolean cells only, FALSE < TRUE; text `=`/none matches Text cells by wildcard, `<>` matches every non-error cell that is not a wildcard-matching Text cell (blanks, numbers and booleans included), ordering operators match Text cells only by ordinal upper-invariant order. Empty operand: no operator or `=` is the empty criterion; `<>` alone matches every non-Blank cell (so `""` text matches); `<`, `>`, `<=`, `>=` compare against empty text. Error cells never match anything.
- **sum_range / avg_range.** Anchored at their top-left, resized to `range`'s dimensions; positions off the grid are Blank. Only Number cells are aggregated; an Error at a matched position propagates (first in row-major order). Omitted → `range` itself. A non-reference `range`/`sum_range` is `#VALUE!` (or its own error). AVERAGEIF with no numeric match → `#DIV/0!`.
- **Efficiency (§12).** Blank positions are never visited. If the criterion cannot match a Blank cell, SUMIF/AVERAGEIF walk `range`'s non-blank cells and read the paired sum cell; if it can (`""`, `=`, `<>x`, ...), they walk the non-blank cells of the (grid-clipped) resized sum region and test the paired range cell, since a blank sum cell contributes nothing. COUNTIF counts blank positions as `CellCount - nonBlank`.

## Phase 3: date functions (§7.6)
- **Serial system (§7.6).** `DateSerial.TryFromYmd` normalizes months by floor division (year must land in 1900..9999), then `FirstOfMonth + d - 1` and requires 0..2958465; `FirstOfMonth(1900,1)=1`, `(1900,2)=32`, later months `DateOnly` day number minus that of 1899-12-30. `ToYmd` maps 0 → (1900,1,0), 60 → (1900,2,29), 1..59 via 1899-12-31 and ≥61 via 1899-12-30. Brief literals were all confirmed by an independent `DateOnly` computation (2025-02-01 = 45689, 2023-12-31 = 45291, 1924-01-01 = 8767, 2024-02-29 = 45351, 9999-12-31 = 2958465); none needed correcting.
- **Arguments (§7.6, §6.9).** Every numeric argument is coerced and truncated toward zero (not floored), so `YEAR(45291.9)` = 2023 and `YEAR(0.9)` = 1900. `DATE` maps years 0..1899 to +1900, rejects <0 and ≥10000; a text year such as `"a"` is `#VALUE!`. YEAR/MONTH/DAY and WEEKDAY/EDATE/EOMONTH reject serials outside 0..2958465 with `#NUM!` (the spec states this for YEAR/MONTH/DAY; applied to the others for consistency). WEEKDAY's type is truncated; types other than 1, 2, 3 are `#NUM!`.
- **EDATE/EOMONTH (§7.6).** The target month is computed in 64-bit; a target year outside 1900..9999 is `#NUM!`. The day clamp and EOMONTH use 29 days for 1900-02 (the fictitious leap day, as Excel), so `EOMONTH(DATE(1900,1,31),1)` = 60. Behaviour for `s < 61` is otherwise as computed from `ToYmd` (spec: unspecified).
- **DAYS (§7.6).** `INT(end) - INT(start)` with INT as the floor (like the INT function), no serial range check.

## Phase 3 fix round 1 (Tasks 4-6)
- **INDEX non-positive index (§7.4; controller ruling, Excel).** A negative `r` or `c` is `#VALUE!` like zero; only a positive index past the range is `#REF!`. Supersedes the earlier "negative is #REF!" note.
- **Approximate lookups consider same-kind keys only (§7.4; controller ruling, Excel parity; spec leaves unsorted/mixed columns unspecified).** VLOOKUP/HLOOKUP/MATCH 1 and -1 compare only keys of the lookup value's kind (a Blank lookup value counts as 0). The binary search uses the nearest same-kind key in the current window when the probe is blank, an error or another kind; with none the search ends. No same-kind qualifying key is `#N/A`. This supersedes the earlier "Compare kind order" behaviour for approximate search. Worst case is an outward scan per step (linear), typical case O(log n).
- **Criteria `<>TRUE`/`<>FALSE` (§7.5; controller ruling).** Match every non-error cell that is not an equal Boolean (blanks, numbers, text included). Numeric-operand `<>` stays numeric-only (§6.10 item 8).
- **Dates range-check before truncation (§7.6).** Any serial below 0 (e.g. `YEAR(-0.5)`) is `#NUM!` for YEAR/MONTH/DAY/WEEKDAY/EDATE/EOMONTH; values above 2958465 after truncation are also `#NUM!`.
